# 网关开发指南

## 当前网关能力

`believe-gateway` 基于 Spring Cloud Gateway 5.0 WebFlux 架构，承担统一流量入口职责。

| 过滤器 | Order | 职责 | 偏内/外网 |
|--------|-------|------|-----------|
| `AuthGlobalFilter` | -2 | JWT 认证 + 白名单放行 | 外网必须 |
| `TraceIdGlobalFilter` | -1 | 生成/传播 TraceId | 两者都需要 |
| `RateLimitGlobalFilter` | 0 | QPS 限流（策略模式：滑动窗口/Sentinel） | 外网必须 |
| `GrayReleaseGlobalFilter` | 1 | 灰度发布路由 | 两者都可能 |
| `RequestLogGlobalFilter` | 5 | 请求日志审计 | 两者都需要 |

从过滤器组合来看，当前网关实际承担的是**外网网关**角色——JWT 认证、限流、白名单，都是面向外部流量的安全面。

## 内网网关 vs 外网网关

| | 外网网关 | 内网网关 |
|---|---|---|
| **流量来源** | 公网、客户端、第三方 | 内部服务间互调 |
| **核心职责** | 认证鉴权、限流熔断、防攻击 | 服务路由、负载均衡、协议转换 |
| **安全等级** | 高——面向不可信流量 | 中低——流量已在信任域内 |
| **证书/加密** | 必须 HTTPS | 通常内网 HTTP |
| **典型组件** | WAF、JWT 校验、IP 黑白名单 | 灰度路由、多版本路由、Mock 路由 |

### 职责边界

- **外网网关**管「谁能进来」——认证、安全、防护是核心。
- **内网网关**管「进来之后往哪走」——路由、版本、协议是核心。

## 什么时候需要内网网关

内网网关不是一开始就需要，以下信号出现时才值得引入：

### 1. 服务数量 > 20~30

服务间点对点调用变得不可维护。每个服务都要维护一份下游地址、重试策略、熔断规则，此时统一的服务路由层能消除重复。

### 2. 多版本并存

A/B 测试、金丝雀发布、蓝绿部署。内网网关做版本路由比每个调用方自己实现灰度逻辑更干净——灰度规则集中管理，调用方无感知。

### 3. 跨协议调用

HTTP ↔ gRPC ↔ Dubbo 互转。一个服务对外暴露多种协议，或者内部不同团队使用不同协议栈，网关做协议转换比每个服务自己适配更高效。

### 4. 统一治理需求

- 全链路压测流量染色
- 内部 Mock 路由
- 请求重放与流量录制
- 服务降级降级统一编排

### 5. 多机房 / 多集群

需要就近路由或异地容灾切换时，内网网关作为流量调度中枢，比在 DNS 层面做更灵活。

## 演进建议

```
阶段 1：服务 < 10
  一个外网网关 + Nacos 服务发现
  服务间通过 Nacos 发现 + Feign/Dubbo 直调
  
阶段 2：服务 10~30，多版本需求出现
  外网网关剥离为独立部署
  引入内网网关做灰度路由和金丝雀发布
  
阶段 3：服务 > 30，多机房/多协议
  外网网关 + 内网网关分层部署
  内网网关承担协议转换和跨机房路由
```

以目前 3~4 个服务的体量，一个网关覆盖全部职责即可。当服务拆分到 20+ 且出现多版本发布需求时，再考虑拆出独立的内网网关。
